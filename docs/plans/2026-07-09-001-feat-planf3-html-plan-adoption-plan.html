Summary

Adopt planf3's plan-artifact mechanics into sl-plan's existing HTML output mode: a canonical HTML plan template that leans heavily on planf3's own template, AI-generated raster images embedded by a bundled script (never by the model), in-plan status markers that interactive sl-work updates as units complete, and an append-only living-artifact layer (metadata lists + Amendments). Markdown plans and the unattended pipeline are untouched; the goal guard stays fully intact.

Problem Frame

sl-plan's HTML mode composes free-form from a section contract, so plan shape varies run to run, plans carry no images beyond hand-authored SVG, and execution progress lives only in git and the task tracker. The planf3 skill demonstrates that a literal stamped template — placeholders, per-section generated images, in-artifact status markers, append-only metadata — is what frontier models reproduce most consistently, and it makes the plan a living artifact any fresh agent can resume from. Super-looper wants those mechanics without giving up its own contracts: the single self-contained file invariant, stable IDs, section vocabulary that sl-work greps, the goal guard, and git as the authoritative progress record.

Requirements

Template and artifact

  • R1. HTML plans are stamped from a canonical template adapted directly from planf3's template (in its SKILL.md): {{PLACEHOLDER}} tokens, <!-- repeat --> blocks, a <details> metadata header, hero/problem/solution image slots, unit blocks with per-task checklists, a per-unit Testing Strategy with a 🔁 validation loop, global Validation Commands, a free-form Notes canvas, and an append-only Amendments section.
  • R2. The template preserves super-looper's HTML contracts: section-heading vocabulary from the section contract, stable R-IDs/U-IDs as anchors and visible text, single self-contained file, all metadata as visible text, composition-signal footer, default-closed collapsibles.
  • R3. Metadata extends the existing field contract additively: title/type/date/origin keep their names (planf3's created maps to date); new append-only list fields are added — modified, commits, agent, session, back refs, forward refs. No field is ever renamed.

Images

  • R4. A bundled stdlib-only python3 script generates images via OpenAI's images API (gpt-image-2), requests webp with compression from the API (no local transcoding), and injects the base64 data URI into the named slot in the HTML file itself. The model never reads or writes base64 payloads.
  • R5. Image failure never blocks the plan: absent key, invalid key, rate limit, network error, and unknown-model all degrade to the same visible-reason skip, leaving slots as placeholder comments. Re-runs fill only empty slots; a named slot can be forced to regenerate.
  • R6. Image prompts are authored by sl-plan at plan-write time into the slot comment grammar, following planf3's prompt rules: wide format, one or two core ideas, under 10 words of text in the image, visual identity synced to the page palette.

Completion tracking

  • R7. During interactive execution of an .html plan, sl-work updates status markers — [] idle, [wip] in progress, [x] complete, [f] failed — at its existing task-lifecycle hook points, using unit/task-text-bearing edit anchors.
  • R8. Markers are advisory; git is authoritative. On resume, sl-work recomputes each unit's real state from code and verification, corrects stale markers (including crash-orphaned [wip]), and never trusts a marker as resume state. [f] is informational — shipping gates on verification, not marker state.
  • R9. Ship-time metadata appends (modified timestamp, commit SHAs, session id) are idempotent — entries already present are never duplicated.

Safety and existing contracts

  • R10. In unattended mode (mode:unattended, lfg, loop.sh) and in parallel-worktree execution, sl-work makes zero writes to the plan file. The goal guard's checksum and PreToolUse hook are untouched. For loop.sh --plan-file runs against an HTML plan, images are baked before the run; the image script never runs mid-loop.
  • R11. The markdown plan contract is unchanged: no status field, progress derived from git, pipeline mode still forces markdown output.
  • R12. Post-run sync: after an autopilot run, an interactive sl-plan resume on the HTML plan backfills what the run could not write — commit SHAs from git, a modified timestamp, and one Amendment entry summarizing the run.
  • R13. The byte-duplicated shared rendering references (html-rendering.md, markdown-rendering.md) are not edited; all carve-outs live in sl-plan-local and sl-work-local files, so the cross-skill byte-identity tests stay green.

Quality and efficiency

  • R14. Contract tests and behavioral evals land in the same change: a new bun test pinning the template's invariants, a new sl-plan eval suite, and a revision of the sl-work eval that currently pins "does not edit the plan body".
  • R15. The work introduces no new LLM sub-agent dispatches (image generation is script-only). Documentation states the model split: author plans on the top-tier model, execute via loop.sh which already defaults to --model opus.

Key Technical Decisions

  • K1 — Template lives in a new sl-plan-local reference, not the shared rendering reference: html-rendering.md is byte-duplicated into sl-brainstorm and sl-ideate and content-pinned by tests; a plan-specific template there would triple-fan-out and shift that file's philosophy. A sibling reference loaded only on the sl-plan HTML path costs nothing elsewhere.
  • K2 — planf3's template is the base; colliding headings map to contract vocabulary: downstream consumers grep section names, so planf3's structure is kept but its headings are renamed where they collide (see mapping in High-Level Technical Design). Everything else — metadata <details>, figures, checklists, loops, Notes, Amendments — carries over near-verbatim.
  • K3 — stdlib urllib script with API-side webp: the repo has no uv or third-party-dependency precedent for bundled scripts, and stdlib Python cannot encode webp. The OpenAI images API accepts output_format: webp + output_compression (planf3's own script exposes both), so the script only base64-wraps returned bytes.
  • K4 — Script-side injection: the script replaces the slot comment with the <img src="data:image/webp;base64,..."> element directly. A single 1536×1024 webp is hundreds of KB; routing that through model Read/Edit would burn tokens for nothing.
  • K5 — Slot grammar carries the prompt and survives filling: <!-- image-slot:hero prompt="..." --> opens the slot and a <!-- /image-slot:hero --> closer wraps the injected image, so re-runs can skip filled slots and a named slot can be regenerated after its placeholder is consumed. The script reports found/filled/skipped per slot; a declared-but-missing slot is a warning, never silence.
  • K6 — Markers advisory, git authoritative: sl-work's existing already-shipped detection stays the source of truth; markers are a human-and-agent-readable projection of it. This resolves crash-stale [wip], marker/git disagreement, and keeps the markdown philosophy intact underneath.
  • K7 — Single-writer, interactive-only mutation: unattended and parallel-worktree execution suppress all plan writes. This is what keeps the goal guard, the AGENTS.md goal-change protocol, and lfg's plan-input HTML acceptance all simultaneously safe — lfg needs no changes.
  • K8 — Ownership split of append-only regions: sl-work owns only the modified/commits/session metadata lists (ship time); sl-plan's revision flows own Amendments and the back/forward reference fields. No writer overlaps another's region.
  • K9 — Scoped reads for image-laden plans: sl-work locates sections by grep and reads offset-scoped ranges, skipping data-URI lines, instead of reading a multi-MB HTML file whole. The template keeps each data URI on a single line to make skipping mechanical.
  • K10 — Model id pinned as a single constant: gpt-image-2 (planf3 pins snapshot gpt-image-2-2026-04-21); an unknown-model API error degrades identically to key-absent. Implementation verifies the id against the live API before landing.

High-Level Technical Design

Two flows share the artifact. The create flow stamps the template and fills image slots script-side; the execute flow splits hard on mode — interactive execution writes markers and metadata, unattended execution never touches the file, which is what keeps the goal guard's checksum valid.

Marker lifecycle within one task. Resume never trusts the stored marker — it recomputes from git/verification and corrects the projection.

U3Image generation script

Goal
Bundled script that generates and embeds all of a plan's images without any model-token cost.
Requirements
R4, R5
Dependencies
U1 (slot grammar)
Files
plugins/super-looper/skills/sl-plan/scripts/generate-plan-images.py (new)
Approach

Stdlib-only python3 (repo convention; adapted from planf3's script but replacing the openai SDK + dotenv with urllib.request and env-var reads). CLI: generate-plan-images.py <plan.html> [--slot <name>] [--regenerate <name>] [--size 1536x1024] [--quality high]. Behavior: parse slot comments; for each empty slot, POST to the images API with the slot's prompt, model pinned per K10, output_format: webp, output_compression; write the returned base64 as a single-line data-URI <img> wrapped in the slot's open/close comments (K5); write via temp-file-and-rename with a one-time .bak backup. Key absent → JSON skip report, exit 0, file untouched (riffrec pattern). 401/429/5xx/network/unknown-model → same skip path per slot, partial fills preserved. Emit a JSON summary: slots found/filled/skipped with reasons; declared-but-missing slot names are warnings. Follow the sl-compound guarded invocation pattern so the skill-conventions platform-var test passes.

Test scenarios
  • No key: exits 0, file byte-identical, JSON reports every slot skipped with reason.
  • Malformed/missing named slot: warning in summary, nonzero warning count, no silent no-op.
  • Re-run on partially filled plan: filled slots untouched, empty slots attempted.
  • --regenerate hero on a filled slot: image replaced within the slot wrappers.
  • Simulated API error mid-batch (mock/urlopen failure): earlier fills preserved, later slots reported skipped, exit 0.
  • Live smoke (implementation-time): pinned model id verified against the real API; response is webp bytes.
Verification

Script self-check (--help + no-key dry run) passes; a real key fills a sample plan's slots and the file opens in a browser with images rendered.

Risks & Dependencies

Risk · mitigated

Goal-guard composition. An unattended run over an HTML plan whose executor writes markers would exit 8. Mitigated by the load-bearing unattended gate (U4), the zero-write eval (U8), and baking images pre-run — with the explicit note that in seed mode sl-work's own gate is the only guard.

Risk · mitigated

Context blowup from embedded images. Multi-hundred-KB single-line data URIs in a file sl-work reads. Mitigated by API-side webp compression, the image-count cap guidance, single-line URIs, and scoped grep/offset reads (K9).

Risk · open

OpenAI API surface drift. The pinned model id or webp output support could change. Contained to one constant in one script; every API failure mode already degrades to placeholder slots, so drift breaks images, never plans. Verify live at implementation (U3 smoke).

Risk · accepted

Repo bloat from committed images. Plans are committed (loop.sh requires it), so embedded webp enlarges history and PR diffs. Accepted as the cost of the single-file invariant; documented with cap guidance (U6).

Dependency: an OPENAI_API_KEY with images access, for the U3 live smoke and for any user who wants filled slots. Everything else is repo-internal.
